## 1. How to read this plan

- **IDs and issues.** One work package (WP) is one GitHub issue created from `.github/ISSUE_TEMPLATE/agent_task.yml` and titled `[WP-nn] <title>` as that template prescribes; the issue body summarises the row and links here. Branches are named `agent-<name>/issue-<n>` (`coordination/README.md` §3). A PR uses `.github/PULL_REQUEST_TEMPLATE.md`, closes its issue with `Closes #n`, carries the handoff block from `coordination/HANDOFF_TEMPLATE.md`, and is squash-merged by the founder. The working protocol lives in `coordination/README.md`; this plan does not repeat it.
- **Owner → Reviewer.** The owner authors the PR; the reviewer is always a different agent (AGENTS.md §6). Default pairs follow `coordination/README.md` §4: Gemini → Codex; Codex → Claude; Claude → Codex. The founder merges every PR and is the only human in the loop; "founder" as reviewer means a read-through, not a code review.
- **Sizes.** S, M and L are relative, not time estimates: S is a single-sitting change with one obvious verification; M is a self-contained feature or document; L is the largest unit allowed in one PR (a build target with its tests). A package that outgrows L is split; the remainder becomes a new issue rather than a half-merged PR.
- **Labels** (created in WP-03): `agent:claude`, `agent:codex`, `agent:gemini` (owner), `in-progress` (an agent has picked the issue up), `needs-review` (on PRs, removed by the reviewer), `needs-triage` (the template's default, and follow-up issues agents open; the founder or Claude Code assigns), `blocked` (dependencies unmet), `spec` (document work), `build-gate` (anything the tracker's Phase 1 Build Gate depends on). Milestones M0–M5 are GitHub milestones without due dates (Roadmap §4).
- **Spec abbreviations** as in AGENTS.md §4: DM, FTS, CM, RB, MR, MC, FSM, NFR, PRD; "tracker" is `docs/PROJECT_TRACKER.md`. Section numbers refer to the versions being frozen in Phase 1 (DM v1.3, MR v1.1+, FTS v1.2, CM v1.2, RB v1.2); where a v1.3 name is not yet final (for example the audit tail-lock function) the WP says so.
- **Repository layout** the outputs assume (MR §7.1, DM §9.2, RB §9): `familylifeos/kernel/` (kernel), `familylifeos/sdk/` (module SDK), `modules/<module_id>/` (manifest and agent per module), `migrations/versions/` (Alembic, DM naming), `wiremock/<dpi>/mappings/` (simulator stubs), `tests/{unit,integration,crash_scenarios,dpi_contracts,e2e,load,fixtures}`, `web/` (PWA: React, Vite, TypeScript, Vitest), `ops/` (Compose profiles, Prometheus, Grafana), `tools/` (scripts).
- **No dates.** Neither this plan nor the Roadmap carries target dates or an assumed number of founder hours (founder ruling 2026-09-17). The order within and across phases is the dependency order, and that is the whole schedule.

Notes on specific packages:

- **WP-03.** Branch protection on `main`: pull request required; the `lint`, `unit` and `integration` checks required; linear history; no force pushes; administrators **not** included, so that `coord:` commits to `coordination/STATUS.md` and `coordination/inbox/` can go straight to `main` (`coordination/README.md` §5). Everything else goes through a PR by convention and by review. Approvals cannot be required because the agents do not hold GitHub review accounts, so the founder's merge is the approval. The issue template (`agent_task.yml`) already has fields for WP id, agent, goal, governing spec sections, definition of done, verification, inputs and size, so an agent can start from the issue alone; WP-03 only checks that its DoD text matches §7. CODEOWNERS is optional: mapping `docs/specs/`, `docs/runbooks/` and `AGENTS.md` to the founder makes Gemini's prohibited paths visible in the PR UI.
- **WP-04.** Issue creation is staged so the board never shows work that cannot start: Phase 0–1 issues from Appendix A now; Phase 2 issues at M1 (after WP-11, so they cite frozen section numbers); Phase 3 at M2; Phase 4 at M3. Dependent issues carry `blocked` until their dependencies close.
- **WP-05.** `pyproject.toml` pins Python 3.12 and declares the runtime dependencies (FastAPI, uvicorn, SQLAlchemy with asyncpg, Alembic, redis, Pydantic, httpx, structlog) and the dev group (pytest, pytest-asyncio, testcontainers, pytest-playwright, ruff, import-linter, pre-commit, coverage). The import-linter contract encodes MR §7.1 as a forbidden contract (`modules.*` may not import `modules.*` or `familylifeos.kernel.*`) plus a layered contract (`familylifeos.sdk` may not import `familylifeos.kernel`); `tools/check_importlib.py` greps `modules/` for `importlib` and `__import__` (MR OI-5).
- **WP-06.** Jobs run on `ubuntu-latest` with the uv cache; `integration` relies on the runner's Docker for Testcontainers; the coverage report is uploaded as an artefact and stays informational until WP-32 turns it into a gate.
- **WP-07.** The roster, the roles and the session close-out rule were added to AGENTS.md §6 on 2026-09-17; what remains is the DoD reference check and Codex's read-through.
- **WP-47.** Deliberately not an MCP server and not a third-party package: a script the repository owns, calling Ollama's local HTTP API with the standard library only, run by Gemini from the terminal. No network access other than `localhost:11434`; no file writes outside the path given on the command line; the prompt, the input files and the output path are arguments, so every delegation is reproducible from the PR. The workflow file limits delegation to mechanical subtasks with a verifier (docstrings, fixtures from a table, format conversions) and repeats that Gemini's restrictions apply to delegated work. An MCP wrapper can come later if the script proves useful.
- **WP-08.** The first maintenance issue also asks Codex for `tools/tracker_sync_check.py`, which compares the status tables in README and AGENTS.md §3 with the tracker's Document Status Matrix; from then on Gemini runs it as its verification.

## 7. Definition of Done (applies to every work package)

A PR is mergeable only when all of the following hold. The PR template (WP-03) carries this list as checkboxes.

1. **Spec reference cited.** The PR description names the WP id and the spec sections it implements (for example "WP-24: FTS §6.1.1–6.1.3, §6.4"), links the issue with `Closes #n`, and carries the handoff block from `coordination/HANDOFF_TEMPLATE.md`.
2. **Tests.** New or changed behaviour has tests; tests that protect an AGENTS.md §4 invariant are named after it (for example `test_invariant_16_idempotency_key_persisted_before_external_call`); unit and integration suites are green in CI; for `build-gate` packages the crash suite and the E2E test are green too.
3. **Docs updated.** README, `Development_Environment_Setup.md` or a runbook is updated when setup or behaviour changes; spec content is linked, never copied (AGENTS.md §6).
4. **Tracker row updated.** The Document Status Matrix, the Build Gate checklist or the change log carries a dated line for the package.
5. **Reviewed by a different agent** than the author, with the review recorded on the PR; the reviewer removes `needs-review`; the founder squash-merges. No self-review, no self-merge (AGENTS.md §6; `coordination/README.md` §4).
6. **No frozen-spec edits without a version bump**, a governance-table row and updates to every dependent document (AGENTS.md §6). Gemini (and any local model it delegates to) never edits `docs/specs/`, `docs/runbooks/` or AGENTS.md.
7. **No secrets or PII.** No `.env`, tokens, consent handles, push tokens or real personal data; test data is the DM §8 Sharma seed or synthetic.
8. **Static checks pass.** `ruff`, import-linter and the `importlib` grep are green; coverage does not fall below the gate once WP-32 enables it.
9. **Size respected.** A package that outgrows L is split; the remainder is filed as a follow-up issue labelled `needs-triage` (agents do not assign it to themselves) rather than merged half-done.
10. **Verification shown.** For Gemini output (including anything it delegated to a local model), the verifying script or test named in the WP row was run and its output is pasted in the PR.

### 7.1 Reviewer checklist by package type

- **Build-target code (WP-20 to WP-31, WP-33 to WP-41):** the five gates run in FTS §2.2 order; the idempotency key is generated once and reused on every retry and Healer path; the resource lock is released only after the Phase 2 COMMIT; audit `details` carry UUIDs and paise only; module code imports nothing outside the SDK; DB grants match MR §7.2; every new error is a FIN or MOD code with an i18n key, never a raw string; the tests for the invariants the package touches are named after them.
- **Documents (WP-07, WP-11 to WP-16, WP-42, WP-44):** governance row and status line present; section references resolve (`tools/xref_check.py`); no spec content duplicated from another document; frozen documents untouched unless the PR is the version bump; the tracker row updated in the same PR.
- **Generated artefacts (WP-14, WP-16, WP-18, WP-19, WP-34):** the verifying script or test output is in the PR; stubs match the WP-12 scenario table row by row; the migration matches the DDL by the schema-diff test, not by reading; no fixture contains a real-looking phone number, Aadhaar number, VPA or account number.
- **Maintenance PRs (WP-02, WP-08):** the diff is limited to the paths the issue names; nothing under `docs/specs/`, `docs/runbooks/` or AGENTS.md; the verification command in the summary actually passes.

### 8.1 When the critical path stalls

- There are no dates to slip against. The signal that the path has stalled is a critical-path issue that stays `blocked` or `in-progress` across several founder sessions; the response is to cut scope, not to push harder.
- Scope is cut in this order: WP-40 voice stand-in (typed intents remain); WP-38 age-18 trigger; WP-37 beyond members and proxies (devices and module activation stay); the k6 run in WP-41 (metric names and dashboard stay); the length of WP-45 (a 2–3 minute video is acceptable).
- Never cut: the crash-scenario suite (WP-28), the threat model before deployment (WP-42), the boundary statement in every artefact (GTM_Plan §7), or a different-agent review on any PR.
- If the Build Gate (M2) proves much harder than expected, Phase 3 is reduced to the Vault (WP-33, WP-34) and the Health slice moves beyond the horizon; the portfolio release then rests on one slice plus the crash suite, which is still a complete story.
